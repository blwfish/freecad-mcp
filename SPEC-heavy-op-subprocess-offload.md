# Spec: Subprocess Offload for Heavy GUI-Thread Operations

**Status:** Draft, written 2026-08-07. Not yet reviewed — per this project's Spec Review Rule (CLAUDE.md), needs a fresh-session cold review before implementation begins. That review should independently re-run the reproduction scripts in "Validation" below against a live GUI instance before trusting this document's diagnosis, per the Spec Review Rule's instruction to verify external-system assumptions rather than take a spec's word for them.

## Goal

Stop FreeCAD (GUI mode) from being killed outright when a client (Claude Code, via this bridge) asks it to do geometry work that takes more than roughly 20–30 seconds. Today this doesn't degrade gracefully — the whole FreeCAD process disappears, mid-session, with no recoverable error. The fix must be a real fix (the operation completes and the caller gets a result), not a workaround that tells callers to avoid the bridge for heavy work.

## Background — diagnosis (2026-08-07 session)

This was chased down empirically in a live debugging session against a real, reproducibly-crashing document (`equipment-hut.FCStd`, a 5-stage chain of `Part::FeaturePython` brick-engraving objects, each built by copying the previous stage's `Shape` and cutting a few thousand more brick/mortar faces into it — `brick_generator`/`quoin_generator` in the sibling `freecad-mr-generators` repo). None of that document's specifics matter to the fix; what matters is it reliably produces single `doc.recompute()` calls that run 20–55 seconds each, chained back to back, five times. That's the trigger — long synchronous GUI-thread work, not anything about this specific document or the geometry it produces.

**What's ruled out, with evidence:**

1. **Not a bug in the geometry computation.** The exact same sequence of `.recompute(True)` calls, on the exact same document, produces correct, valid, non-null shapes 100% of the time (3/3) when run as a plain script via `FreeCADCmd script.py` — no MCP bridge, no AICopilot socket server, no Qt event loop involved at all. Total time for the full 5-stage chain: ~180s, zero errors.
2. **Not a crash.** Every death during today's session was checked against `~/Library/Logs/DiagnosticReports/` (via this repo's `FC-tools/crash-capture/harvest_reports.sh` sibling tool) — zero `.ips` crash reports were ever generated, across roughly 8 separate deaths. macOS's crash reporter (`ReportCrash`) is never invoked for a `SIGKILL` — it can't be, `SIGKILL` isn't catchable by anything, including the reporter — so this is consistent with an external kill but not with a segfault/abort.
3. **Not headless-safe either.** A `spawn_freecad_instance(gui=false)` instance, driven through the identical `execute_python_async`/`poll_job` path, died the same way (confirmed via `ps` showing zombie state, `PPID` matching the bridge process). It still goes through the same `_process_gui_tasks` queue (`freecad_mcp_handler.py:579`) — headless FreeCADCmd launched by AICopilot still runs a Qt event loop for this dispatch mechanism to work at all, and blocks it the same way GUI mode does.
4. **Not anything in this codebase's own code.** `FreeCADHealthMonitor.attempt_restart()` (`AICopilot/freecad_health.py:327`) is the only `os.kill(..., SIGKILL)` call anywhere in `freecad-mcp` or `AICopilot` — grep-confirmed. It's dead code: never called from any live path, only from a commented-out line in that file's own `if __name__ == "__main__"` demo block. `freecad_mcp_handler.py`'s only interaction with the health monitor module is `_monitor.socket_path = ...` and `_monitor.log_crash(...)` (line 1194) — logging, not killing.
5. **Not a graceful, catchable shutdown either — this is the load-bearing finding.** Before the last reproduction, the live FreeCAD instance was instrumented from Python (`atexit.register`, a patched `sys.exit`, and `QApplication.aboutToQuit` connected + `.quit` patched — all logging a full multi-thread stack dump to a file on any trigger). The instrumentation was confirmed installed (its own "installed" log line is present). The process was then driven through the same crash-reproducing sequence and died ~36s in. **Nothing in the instrumentation log fired** — no `atexit`, no `sys.exit`, no `aboutToQuit`, no `.quit()` call. This rules out any Python-level or Qt-level code (in FreeCAD, AICopilot, or Qt itself) initiating the termination.
6. **Points at (4) + (5) + (2) together: an external, uncatchable kill (almost certainly `SIGKILL`), triggered by something outside the process,** most plausibly macOS itself reacting to the app's main thread going unresponsive for tens of seconds to minutes at a stretch — though this session could not pin down the exact daemon/mechanism responsible (would need kernel-level log access not available in the sandbox this session ran in). The unified system log around each death (`/usr/bin/log show`, filtered by PID) shows only the *aftermath* — `runningboardd`/`launchservicesd`/`WindowServer` all reacting to the process already being gone (`"termination reported by proc_exit"`, XPC connections invalidating) — never an explicit "X is killing Y" line at the privilege level this session could query.

**Why this specific document/setup makes the mechanism visible:** `freecad_mcp_handler.py`'s own code already anticipated this class of problem — `_gui_unresponsive_error()`'s docstring (line 666) explicitly lists "FreeCAD may have crashed, be blocked in a modal dialog, or be **backgrounded/asleep**" as reasons the heartbeat might go stale, and `GuiHeartbeat`'s module docstring (`AICopilot/gui_heartbeat.py:1-15`) lists "macOS App Nap throttling a backgrounded app" by name. Both are diagnostic-only — they detect staleness after the fact, they don't prevent the underlying block. `_process_gui_tasks` (line 579) runs its whole `while not self._gui_task_queue.empty()` loop, including `task()` at line 615 for async jobs, synchronously inside one `QTimer.singleShot(100, ...)`-scheduled tick (line 664 re-arms the timer only *after* the loop returns). A single 55-second job means the Qt event loop does not run *at all* for 55 seconds — no event processing, no OS-level liveness response, nothing — which is exactly the condition both of those docstrings were already worried about.

**Why this is a second-order consequence of a previous, correct fix, not a new architectural mistake:** `KNOWN_ISSUES.md`'s first entry ("Document Creation from Socket Thread Causes Crashes", fixed 2026-02-27) documents *why* this single-GUI-thread dispatch queue exists at all — calling FreeCAD document APIs from the socket-handler thread caused real GIL/Qt deadlocks, and routing everything through one `QTimer`-driven queue on the main thread fixed that. That fix is still correct for what it targets (thread-safety). This spec's problem is a different failure mode of the same mechanism: it never anticipated a *single* queued task running long enough to make the whole app look dead to the OS.

## Design

Add a new MCP tool, `execute_python_heavy`, implemented **entirely in the bridge** (`freecad_mcp_server.py`) — no changes needed to `AICopilot/` (the code running inside the live FreeCAD process) beyond what it already exposes. This is a deliberate scope choice: it reuses the bridge's own already-proven subprocess machinery (`_find_freecad_cmd_binary()` and the `subprocess.Popen` pattern around `freecad_mcp_server.py:2788`, both already exercised by the existing `spawn_freecad_instance` tool) rather than teaching the in-process socket server to spawn its own subprocesses.

Client-facing contract matches `execute_python_async` exactly — same `code` argument, same `job_id`/`poll_job`/`cancel_job` lifecycle — so any caller who already knows to reach for `execute_python_async` for long operations only has to change the tool name, not the calling pattern. The tool description should say explicitly: use this instead of `execute_python_async` when the operation is expected to run more than ~20-30s and does *not* need to read or set GUI-only state (selection, 3D view, active workbench) mid-execution — see Non-goals.

### Sequence (bridge-orchestrated, no AICopilot changes required)

All three GUI-thread round-trips below (a), (d), and the failure path are ordinary `execute_python`/`execute_python_async` calls the bridge already knows how to make — each is a small, fast snippet (well under a second of actual work), never the heavy `code` argument itself. The heavy part never touches the GUI thread.

1. **(a) Snapshot.** Bridge sends a small `execute_python` call to the live GUI instance: get `App.ActiveDocument.Name` and `.FileName`. If `FileName` is empty (never saved), return an error telling the caller to save the document first — auto-saving to an unnamed temp path on the caller's behalf is out of scope (see Non-goals). Then send `doc.save()` so the subprocess has a known-current starting point.
2. **(b) Dispatch.** Bridge writes a small wrapper script to a temp path (same pattern as this session's manual repro): open the document by the path from (a), `exec()` the caller's `code` with `FreeCAD`/`App`/`Part`/`Vector` bound, then `doc.save()` again on success. `ExecutePythonOpsHandler.run_code`'s namespace (`AICopilot/handlers/execute_python_ops.py:46-57`) additionally binds `FreeCADGui`/`Gui` for the live-GUI case — the offload wrapper should deliberately **not** bind these (headless `FreeCADCmd` has no working 3D view/selection for them to operate on), so code relying on `Gui`-namespace symbols fails clearly rather than silently misbehaving; see Non-goals. Bridge spawns the wrapper via `subprocess.Popen([freecad_cmd_binary, wrapper_path])`, non-blocking, using the exact discovery logic `spawn_freecad_instance` already uses.
   - Worth noting as precedent for step (a)'s save-before-heavy-work: `run_code` itself already auto-saves the active document before running *any* submitted code, specifically so a crash mid-execution doesn't lose work (`execute_python_ops.py:62-70`, comment: *"If the code triggers a crash (e.g., .check() on huge compounds, boolean ops on 1000+ solids), the saved file survives."*) — this spec's snapshot step is the same idea, just also handing that saved state to a subprocess rather than only using it for crash recovery.
3. **(c) Poll.** Bridge stores the `Popen` handle plus a `job_id` in a new bridge-side (not AICopilot-side) job table. `poll_job(job_id)` for this job type checks `proc.poll()` — instant, non-blocking, no GUI-thread involvement at all. While running: status `"running"`. On exit 0: proceed to (d). On nonzero exit: capture stderr, surface as `status: "error"`.
4. **(d) Merge back.** Once the subprocess exits 0, bridge sends one more small `execute_python` call to the live GUI instance: close the in-memory document by name and re-open it from the same path the subprocess just saved to (`App.closeDocument(name); App.openDocument(path)`). Report `status: "done"` to the caller once this completes.
5. **Timeout / cancel.** `cancel_job(job_id)` on a job of this type calls `proc.terminate()`, escalating to `proc.kill()` if it doesn't exit within a few seconds — safe regardless, since it's a separate process; the live GUI FreeCAD is never at risk. Add a configurable max runtime (default suggestion: 10 minutes) enforced the same way from the polling loop.
6. **Concurrency.** Serialize: reject a second `execute_python_heavy` call against the same document while one is already pending against it (same document = same `FileName`), to avoid two subprocesses racing to save to the same file. Different documents/instances can run concurrently — no shared state between them.

### What this buys, beyond just "doesn't get killed"

- **Safe cancellation.** Today, there is no way to stop a runaway `execute_python_async` job without losing the whole live FreeCAD session (killing the GUI process kills everything, including anything else open in it). A subprocess job can be killed cleanly at any point.
- **Bounded blast radius.** A bug in the caller's `code` that genuinely hangs forever (not just "slow") no longer threatens the interactive session — it threatens a disposable subprocess.

## Alternatives considered

- **Periodically pump the Qt event loop (`processEvents()`) during the operation, in-process.** Rejected: there's no way to interleave this *inside* a single call like `doc.recompute()` — it's one atomic C++ call from Python's perspective. Doing this for real would mean patching FreeCAD's own recompute implementation to yield periodically, a much larger and riskier change than a bridge-side Python fix, and it might not even fully solve the OS-responsiveness half of the problem if the actual signal macOS cares about isn't purely "did Qt process an event recently."
- **Run the heavy call on a background *thread* within the same live FreeCAD process, instead of a separate process.** Deferred, not rejected outright — lower overhead than a subprocess (no document save/reload round trip, no losing 3D view camera state), but FreeCAD's document APIs are documented as unsafe for concurrent multi-thread access, and it's genuinely unclear whether a single dedicated worker thread that never overlaps with the GUI thread's own document access would be safe in practice. The subprocess approach is empirically proven (this session ran it three separate times against the real crash scenario, zero failures); a thread-based approach is not, and would need real investigation against FreeCAD's actual thread-safety guarantees before being trusted. Worth revisiting later as an optimization once the subprocess version is working and if the reload-losing-view-state cost turns out to matter in practice.
- **macOS `NSProcessInfo` "disable automatic termination" / "begin background activity" APIs.** Investigated during diagnosis: `FreeCAD.app`'s `Info.plist` (`FC-clone/build/release/src/MacAppBundle/FreeCAD.app/Contents/Info.plist`) sets neither `NSSupportsAutomaticTermination` nor `NSSupportsSuddenTermination`, so this isn't confirmed to even be the actual mechanism — and finding #5 above (nothing in the instrumented shutdown path fired) argues against a *graceful* macOS-initiated termination specifically, which is what those APIs govern. If a fresh session wants to spend an hour on this before building the subprocess fix, it's a much cheaper change *if* it turns out to be the real cause (plausibly a few lines using PyObjC at AICopilot startup) — but should be verified against a live crash reproduction first, not assumed. Not the primary recommendation because it's unverified and the subprocess approach is proven regardless of which OS mechanism turns out to be the actual killer.

## Explicit non-goals

- **No `FreeCADGui`/`Gui`/selection/view access inside the offloaded code.** The subprocess is headless `FreeCADCmd` — there is no 3D view, no selection, no active workbench. Code that needs any of that must keep using `execute_python`/`execute_python_async` as today. The tool description should say this plainly so callers don't reach for it by mistake and get a confusing `NameError` on `Gui`.
- **No auto-save-to-temp-path for never-saved documents.** If `App.ActiveDocument.FileName` is empty, error out and tell the caller to save first, rather than silently picking a path on their behalf.
- **No attempt to preserve 3D view camera position / selection / undo history across the reload in step (d).** Reopening the document is expected to reset these. If this turns out to matter in practice, it's a follow-up, not part of this spec.
- **No protection against the caller's document being edited live in the GUI while a heavy job is pending against it.** The subprocess works from the snapshot saved in step (a); any concurrent GUI-side edit during the job's run is going to be lost when step (d) reloads from the subprocess's output. Worth a one-line warning in the tool description; actually preventing it (e.g. locking the document) is out of scope for this spec.
- **Not a replacement for `execute_python_async`.** Both tools continue to exist; this is additive. `execute_python_async` remains correct and preferred for anything short enough not to trigger the problem, or that needs GUI-thread state.

## Validation

Before considering this fixed, re-run the exact reproduction this session used and confirm it no longer kills the process:

1. A document with a `Part::FeaturePython` (or similar) chain where at least one single `.recompute()` call reliably takes 30s+ (this session's `equipment-hut.FCStd` in the sibling `freecad-mr-generators` repo reproduces this out of the box — see that repo's session history from 2026-08-07 for the exact object names).
2. Drive it via the new `execute_python_heavy` tool with `code` that touches/recomputes several such objects in sequence (the original failing case chained 5).
3. Confirm: the call returns a valid `job_id` immediately, `poll_job` reports `"running"` while the subprocess computes, the live GUI FreeCAD process's own PID is untouched and stays responsive to *other* tool calls throughout (this is the actual bug being fixed — verify it, don't just check the job eventually succeeds), and `poll_job` eventually reports `"done"` with the document correctly updated in the GUI.
4. Separately confirm `cancel_job` against a deliberately-slow/infinite `code` argument actually terminates the subprocess and leaves the live GUI instance untouched.

## Open questions for review

1. Bridge-side job table: does it need to survive a bridge restart (i.e. persisted, not just in-memory), given jobs can run for many minutes? Today's `execute_python_async` job table (`_async_jobs`, AICopilot-side) is in-memory only and this spec's design mirrors that — probably fine to keep it in-memory bridge-side too, but worth a second look given the bridge process itself is more likely to be restarted/redeployed during active development than the live FreeCAD GUI session is.
2. Exact default timeout (10 minutes suggested above) — arbitrary, pick something more informed by real heavy-operation durations if there's data.
3. Whether `execute_python_heavy`'s wrapper script should support anything beyond a flat `code` string (e.g. passing structured arguments) — `execute_python_async` doesn't, so parity suggests no, but worth confirming there's no near-term need before locking the interface.
4. Confirm the `NSProcessInfo` alternative (see above) really is a dead end before building the larger subprocess mechanism — it's cheap to check and would substantially shrink this spec's scope if it works.
